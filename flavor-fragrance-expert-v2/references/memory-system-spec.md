# 记忆学习系统规范 (Memory System Specification)

> 本规范定义调香专家的**用户记忆库**结构、知识进库闸门、读取/沉淀机制与文件组织方式。
> 行业通识（书摘、原料卡、法规等）见并行规范 [`domain-knowledge-spec.md`](domain-knowledge-spec.md)，存放于 `.flavor-domain/`，**不得**与用户 `[K0XX]` 混用同一编号序列。

---

## 一、设计目标

1. **越用越懂你**：记录用户的香型偏好、风格倾向、合规要求、特殊限制，避免每次重复询问
2. **配方可追溯**：每次配方生成都留下完整档案，包含需求、推导过程、用户反馈、迭代记录
3. **知识能积累且不被污染**：过程性/差模型测试知识先进候选库；仅用户确认或强证据后进入生效库
4. **记忆可复用**：后续配方设计时只调用生效知识，加速迭代、减少试错

---

## 二、工作区与记忆库目录结构

**工作区根目录写死**（跨 Agent 共享记忆与交付）：
`E:\Data\Claude code\flavor-fragrance-expert\`

```
E:\Data\Claude code\flavor-fragrance-expert\
├── .flavor-memory\                  # 用户记忆库（写死）
│   ├── PROFILE.md                   # 用户偏好档案
│   ├── KNOWLEDGE.md                 # 生效知识（status=active，Phase 0 可调用）
│   ├── KNOWLEDGE-CANDIDATES.md      # 候选知识（默认不可调用）
│   ├── FEEDBACK-LOG.md              # 反馈时间线
│   ├── INDEX.md                     # 配方历史索引（含交付路径）
│   └── formulas/                    # 配方档案（决策摘要 + 链接交付，勿重复堆完整表）
│       ├── coffee/
│       └── ...
├── .flavor-domain\                  # 垂类领域库（见 domain-knowledge-spec.md）
└── deliveries\                      # 交付根目录
    └── coffee\
        └── 2026-07-16_1266甜焦糖_电子雾化_grok-4.5\
            ├── overview.md
            ├── report.md
            └── report.html
```

### 目录创建规则
- 首次使用时，检查并创建 `.flavor-memory/` 完整结构（含 `KNOWLEDGE-CANDIDATES.md`）；同时确保 `deliveries/`、`.flavor-domain/` 根目录存在
- `formulas/` 与 `deliveries/` 下香型子目录：英文小写 kebab-case（`coffee`、`berry`、`tobacco`、`baked-goods`）
- **禁止**使用中文目录名（如 `咖啡`）；INDEX / 档案 / 交付三处命名必须一致
- **交付目录必含模型 slug**：`{YYYY-MM-DD}_{香型简称}_{场景简称}_{模型slug}`
- **记忆与交付分离**：完整配方表以 `deliveries/` 为准；`formulas/` 侧重需求、关键决策、反馈、知识编号与交付路径链接

## 三、知识进库闸门（防污染，必遵守）

### 3.0 三层状态

| 层级 | 文件 | Phase 0 可否调用 | 谁写入 |
|------|------|------------------|--------|
| 候选 | `KNOWLEDGE-CANDIDATES.md` | **否** | Agent 在 Phase 6 可自动追加 |
| 生效 | `KNOWLEDGE.md`（`status: active`） | **是**（且须满足证据规则） | 仅升格流程写入 |
| 拒绝/过时 | 候选中标 `rejected`，或生效条目标 `superseded` | **否** | 用户否决 / 纠正流程 |

### 3.0.1 升格为生效的条件（满足其一）

1. **用户明确授权**：如「记进知识库」「候选 K012、K015 通过」「把糠硫醇上限记住」
2. **多重反馈**：同一规律在不同日期/配方中经用户认可 ≥2 次，Agent **提议升格**，仍须用户点头一次（默认不自动升格）
3. **当轮已确认的低风险偏好**：可写入 `PROFILE.md`；若写入 KNOWLEDGE，须 `evidence: user-confirmed`

### 3.0.2 禁止直接写入生效库

- 仅模型自洽、用户未点评 / 未闻样验证
- 对比实验、较差模型试跑、标注「仅供参考」的交付
- `evidence: model-only` 的条目
- 一次性、无复用价值的细节

### 3.0.3 Phase 0 调用硬过滤

仅加载同时满足的条目：
- 位于 `KNOWLEDGE.md`
- `status: active`（若条目无 status 字段，见下方「旧条目兼容」）
- `evidence` 为 `user-confirmed` 或 `multi-feedback`（**排除** `model-only`）
- 若存在 `supersedes: [K0XX]`，只使用最新 active，不使用被取代条目

**旧条目兼容（grandfather）**：`KNOWLEDGE.md` 中在闸门规则生效前写入、且缺少 `status`/`evidence` 元数据的 `[K0XX]`，Phase 0 **暂按** `status: active` + `evidence: user-confirmed` + `confidence: medium` 对待，避免历史库失效。整理库时逐步补全元数据；用户可随时要求将存疑旧条移入候选或标 `superseded`。

**冲突裁决**：用户已验证经验 > 领域通识（`.flavor-domain`）> 模型临场推理；但**法规硬限制**在合规版中优先于用户「极致还原」偏好。

## 四、各记忆文件规范

### 4.1 PROFILE.md — 用户偏好档案

**定位**：稳定偏好与长期约束（用户画像）。

**更新策略**：每次交互后**合并更新**，保持简洁。「历史交互摘要」最多保留最近 **20** 行，更早可删或移入归档说明。

**模板**：

```markdown
# 用户调香偏好档案

> 最后更新：YYYY-MM-DD | 累计交互次数：N

## 1. 场景偏好
- 主场景：[电子雾化 / 食用香精 / 双场景]
- 常用体系：[PG/VG比例 / 溶剂体系 / 其他]
- 设备特性：[雾化功率范围 / 芯子类型 / 其他工艺约束]

## 2. 香型偏好
- 高频香型：[按频率排序]
- 近期探索：[最近尝试的新香型]
- 回避香型：[明确不喜欢的香型或方向]
- 回避单体/分路：[明确否定的单体或香气方向]

## 3. 风格维度倾向
- 酸甜比偏好：...
- 烘焙度偏好：...
- 还原度 vs 创新度：...
- 体感偏好：...

## 4. 合规要求
- 默认合规标准：...
- 受限组分态度：...
- 特殊法规要求：...

## 5. 输出偏好
- 版本需求：...
- 报告语言：...
- 报告深度：...
- HTML 可视化报告：...

## 6. 工艺与成本约束
- 成本敏感度：...
- 可用原料限制：...
- 量产工艺约束：...

## 7. 历史交互摘要（最近 20 条）
- [YYYY-MM-DD] [香型] [场景] [模型] — [一句话]
```

### 4.2 KNOWLEDGE.md — 生效知识库

**定位**：仅存放**已放行**的可复用规律。Phase 0 唯一用户知识源。

**更新策略**：仅通过「升格」追加；不修改旧条目正文。纠正时追加新条并设 `supersedes`，旧条改标 `status: superseded`（允许改 status 字段）。

**条目必填元数据**：

```markdown
### [K010] 2-糠硫醇用量手感
- status: active
- evidence: user-confirmed
- confidence: high
- source: 2026-07-12 中度烘焙咖啡 / formulas/coffee/2026-07-12-中度烘焙咖啡-雾化版.md
- source_model: grok-4.5
- scene: 电子雾化
- tags: coffee, sulfur, fingerprint
- cas: 98-02-2
- supersedes:
- 规律：0.005‰ 表现良好；超过 0.008‰ 用户反馈「硫味过冲」
- 应用：后续咖啡雾化配方建议 0.003–0.006‰
```

**分类**（编号段建议）：
- K001–K009：用户专属偏好规律
- K010–K019：单体使用经验（含负向用量区间）
- K020–K029：香韵分路经验
- K030–K039：合规替代经验
- K040–K049：雾化适配经验
- K050–K059：反馈模式
- 之后按类追加，全局编号递增不重复

### 4.3 KNOWLEDGE-CANDIDATES.md — 候选知识库

**定位**：过程提炼与未验证规律的 inbox；**默认不参与配方设计**。

**更新策略**：Phase 6 可自动追加；用户「通过」后剪切/复制到 `KNOWLEDGE.md` 并改 `status: active`；否决则标 `status: rejected`。

**模板**：

```markdown
# 调香知识候选库

> 候选数：N | 最后更新：YYYY-MM-DD
> Phase 0 禁止调用本文件中的条目。

### [KC001] 标题
- status: candidate
- evidence: model-only
- confidence: low
- source: ...
- source_model: deepseek
- scene: 电子雾化
- tags: coffee, ...
- cas:
- 规律：...
- 应用（若升格）：...
- 升格条件：待用户确认 / 待二次反馈
```

候选编号使用 `[KC0XX]`，与生效 `[K0XX]` 分离；升格时分配新的 `[K0XX]`，并在候选条目标注 `promoted_to: [K0XX]`。

### 4.4 FEEDBACK-LOG.md — 反馈时间线

**定位**：反馈原始素材；区分「交付时意见」与「闻样/上机后验证」。

**更新策略**：纯追加。

**模板要点**：
- 关联配方档案与交付路径、模型 slug
- **验证状态**：`未验证` / `已口头确认` / `已闻样确认`
- **沉淀**：列出写入候选的 `[KC0XX]`；若有升格则列 `[K0XX]`

```markdown
## [2026-07-15] 意式浓缩咖啡（食用）

**交付路径**：deliveries/coffee/2026-07-15_意式浓缩_食用_grok-4.5/
**模型**：grok-4.5
**验证状态**：已口头确认

**用户反馈**：...
**采纳情况**：...
**候选知识**：→ [KC012] ...
**生效知识**：→（无 / [K012] 用户确认升格）
```

**须记录**：调用的生效 `[K0XX]` / 领域 `[D0XX]`、候选 `[KC0XX]`、交付路径、模型、用户反馈与迭代。

## 五、记忆读取机制（Phase 0）

**触发**：每次配方交互开始时。

**分层加载（控 token）**：

1. **检查** `.flavor-memory/`；不存在 → 首次交互说明，建库后进 Phase 1
2. **必读** `PROFILE.md` + `INDEX.md`（索引表即可）
3. **历史配方**：按香型从 INDEX 取最近 **1–3** 份相关档案（英文目录名）
4. **生效知识**：只读 `KNOWLEDGE.md` 中通过硬过滤的条目；按 `tags` / `scene` / 香型筛选，**禁止**读取 `KNOWLEDGE-CANDIDATES.md` 用于设计
5. **近期反馈**：`FEEDBACK-LOG.md` 中与当前香型相关的最近 3–5 条
6. **领域库**（若存在）：按 [`domain-knowledge-spec.md`](domain-knowledge-spec.md) **按需**检索 `.flavor-domain/`，不整库塞入上下文

**调用优先级**：
1. PROFILE  
2. 用户生效 KNOWLEDGE（active + 合格 evidence）  
3. 领域库相关 `[D0XX]` / 资料卡  
4. 当前输入（GC-MS、需求）  
5. 模型临场推理（缺口处须标「推测」）

**应用**：Phase 1 复述偏好；Phase 3 应用生效 K 与领域资料；输出中分别标注「用户经验 [K0XX]」与「领域资料 [D0XX]」。

## 六、记忆沉淀机制（Phase 6）

**触发**：配方交互完成（交付落盘）或用户给出反馈后。

**流程**：

1. 更新 `PROFILE.md`（合并；摘要≤20 行）
2. 创建/更新 `formulas/{香型英文}/` 档案（链接交付，记录模型）
3. 更新 `INDEX.md`（含交付路径、模型、状态）
4. 确认 `deliveries/.../` 三文件已落盘
5. **提炼规律 → 默认写入 `KNOWLEDGE-CANDIDATES.md`**（`[KC0XX]`，填齐元数据；差模型/未验证标 `evidence: model-only`、`confidence: low`）
6. **仅当用户明确确认（或满足升格条件且用户点头）** → 写入 `KNOWLEDGE.md` 为 `[K0XX]` + `status: active`
7. 更新 `FEEDBACK-LOG.md`（关联 KC/K 编号与验证状态）
8. 告知用户：新增候选 N 条；若有升格则说明生效 M 条；列出候选摘要并询问「哪些进知识库？」
9. **禁止**将模型编造的原料/法规数据写入 `.flavor-domain/`（领域库仅用户导入或用户明确要求时更新）

**沉淀原则**：
- 主动沉淀候选，不依赖用户提醒
- 生效库窄门进
- 可追溯到档案与交付
- 冲突不删旧：新条 `supersedes` + 旧条 `superseded`
- 负向经验（失败用量区间、否定分路）同样可进候选/生效

---

## 七、记忆调用透明化

1. **开头**：列出本次调用的生效 `[K0XX]` 与领域 `[D0XX]`（分两组）
2. **结尾**：列出本次新增候选 `[KC0XX]`；若有升格列出 `[K0XX]`；提示用户确认进库
3. **HTML**：记忆调用章节只展示生效 K；知识沉淀章节区分「候选」与「已升格」

---

## 八、记忆库维护

### 8.1 治理
- 生效条目建议保持精炼；超过约 40 条 active 时提示整理
- 合并重复、`superseded` 可移入文末「归档」区或 `KNOWLEDGE-ARCHIVE.md`
- 候选长期未处理（>30 天）可提示用户批量通过/拒绝

### 8.2 冲突
- 例：`[K035] supersedes: [K010]`，正文写明纠正内容；调用只认 K035

### 8.3 隐私
- 仅存调香相关信息；本地存放；不主动外传
